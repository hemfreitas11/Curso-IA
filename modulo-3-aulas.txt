Por que um Analista de IA precisa saber disso

Agentes de código não são só ferramenta de programador. Quem trabalha com IA usa agentes para montar protótipos, scripts de análise, integrações e avaliações, e precisa trabalhar com quem desenvolve sistemas de verdade. Entender como essas ferramentas evoluíram, o que cada uma oferece e onde elas erram ajuda a usá-las no lugar certo.

Quatro ondas
Autocompletar (2021 em diante). O GitHub Copilot sugeria a próxima linha ou função enquanto você digitava. A IA via só o trecho do arquivo aberto.
Chat (2022 em diante). Com o ChatGPT, desenvolvedores passaram a colar trechos de código e erros no chat. Ajudava a entender e esboçar, mas o fluxo era manual: copiar, colar, testar, voltar.
Editor com agente (2023 a 2025). Editores como o Cursor trouxeram o chat para dentro do projeto. A IA passou a ler o repositório, propor mudanças em vários arquivos e aplicar com um clique, ainda com a pessoa acompanhando cada passo.
Agente autônomo (2025 em diante). Agentes como o Claude Code, o OpenAI Codex e o Google Antigravity recebem um objetivo e trabalham em ciclo (agentic loop): leem o código, planejam, editam, rodam testes, corrigem e repetem até terminar. Rodam no terminal, no editor ou na nuvem, vários em paralelo, cada um numa branch, e devolvem um pull request para revisão.
ONDA	O QUE A IA VÊ	O QUE A IA FAZ	QUEM VERIFICA
Autocompletar	O trecho aberto	Sugere a próxima linha	A pessoa, linha a linha
Chat	O que você colou	Explica e esboça	A pessoa, copiando e testando
Editor com agente	O projeto	Edita vários arquivos e roda comandos	A pessoa, passo a passo
Agente autônomo	O projeto, a saída dos testes, outras fontes	Executa a tarefa inteira em ciclo	Os testes, e a pessoa no fim

O gargalo deixa de ser digitar e passa a ser especificar e verificar.

O panorama das ferramentas

Este mercado muda a cada mês. Mais importante que decorar a lista é entender o estilo de cada uma.

FERRAMENTA	DE QUEM	ESTILO
ChatGPT	OpenAI	Chat geral. Bom para entender, esboçar e tirar dúvidas
Codex	OpenAI	Agente de código no terminal, no editor e na nuvem, onde executa tarefas em paralelo e devolve pull requests
Claude Code	Anthropic	Agente de código no terminal, no editor e no app desktop. Trabalha com arquivos de instrução (CLAUDE.md), skills, subagentes e MCP (aula 3.2)
Cursor	Anysphere	Editor (derivado do VS Code) com IA no centro: autocompletar, chat e modo agente, com modelos de vários fornecedores
Kiro	AWS	Editor com foco em spec-driven development (aula 3.3)
Antigravity	Google	Editor "agent-first": uma visão de gerente para despachar e acompanhar vários agentes, que geram artefatos (planos, capturas) para revisão
GitHub Copilot	GitHub/Microsoft	Do autocompletar original ao modo agente e ao agente que trabalha a partir de uma issue e abre o pull request

Todas têm em comum um modelo de linguagem por trás, a leitura do projeto, a edição de vários arquivos, a execução de comandos com algum nível de permissão, arquivos de instrução do projeto e suporte a MCP. Por isso os conceitos das próximas aulas valem para qualquer uma.

Como escolher
Pela tarefa: ajuste rápido no editor pede um editor com IA; tarefa longa, com testes, pede um agente autônomo; funcionalidade nova com requisitos soltos se beneficia de specs.
Pelo controle: quanto o agente pode fazer sem perguntar (editar, rodar comandos, acessar a rede, fazer push)? Dá para limitar por projeto?
Pelos dados: o código vai para servidores de quem? É usado para treinar modelos? Há opção empresarial com garantias contratuais?
Pelo custo: assinatura fixa por pessoa ou cobrança por uso de tokens. Tarefas longas de agente podem consumir muito.
Pela integração: funciona com o seu controle de versão, o seu processo de revisão e os seus sistemas (via MCP)?
Teste no seu projeto: escolha três tarefas reais de tamanhos diferentes, dê a mesma descrição e o mesmo contexto a cada ferramenta, defina antes o que é "pronto" e anote tempo, custo, quantas correções foram necessárias e a qualidade do diff. É o raciocínio dos evals: decidir com dados, não com impressão.
Vibe coding: onde serve e onde não serve

Vibe coding é pedir, aceitar o que vier sem ler e seguir pedindo até "funcionar". Para explorar uma ideia, montar um protótipo descartável ou um script de uso único, pode ser ótimo. Para um sistema que outras pessoas vão usar, é perigoso: ninguém sabe o que o código faz, os casos de borda não foram pensados e os problemas aparecem em produção.

O que dá errado com código gerado

O risco mais comum não é o código que quebra, e sim o que parece certo. A IA escreve código fluente e bem formatado, e isso baixa a guarda de quem revisa.

RISCO	EXEMPLO	DEFESA
Código errado e convincente	Regra de negócio pela metade; erro engolido; teste que testa a implementação e nunca falha	Critérios de aceite claros, testes dos casos de borda, revisão do diff
Falha de autorização	Consulta sem filtro de cliente, que vaza dado de um usuário para outro	Teste explícito: "o usuário A não vê dados do usuário B"
Dependência inventada	O modelo sugere um pacote que não existe, e alguém registra um pacote malicioso com esse nome (slopsquatting)	Conferir tudo que é novo: existe? quem mantém? há quanto tempo?
Segredo ou dado no prompt	Chave de API ou dado de cliente colado na ferramenta	.env fora do Git e do alcance do agente; dados anonimizados; ferramentas aprovadas
Instruções escondidas	Uma página ou issue com texto que manipula o agente (prompt injection, aula 2.7)	Permissão mínima, confirmação humana em ações sensíveis
Código que ninguém entende	Ninguém consegue manter ou explicar o que o agente escreveu	Quem abre o PR responde por ele; se não sabe explicar, não está pronto

Para praticar: revise este código gerado

Um agente escreveu a função abaixo para uma API de pedidos. Os testes dele passaram. Encontre pelo menos quatro problemas antes de ler as respostas.

import logging

def listar_pedidos(db, usuario, status=None):
    try:
        consulta = "SELECT * FROM pedidos"
        if status:
            consulta += f" WHERE status = '{status}'"
        pedidos = db.execute(consulta).fetchall()
        logging.info(f"Pedidos listados para {usuario.email}: {pedidos}")
        return pedidos
    except Exception:
        return []


Respostas:

Não filtra pelo usuário: qualquer pessoa vê os pedidos de todos.
SQL montado com texto: o status vai direto na consulta, o que permite injeção de SQL. Use parâmetros.
Log com dados pessoais: registra o e-mail e o conteúdo dos pedidos.
Erro engolido: qualquer falha vira uma lista vazia, e ninguém fica sabendo que o banco caiu.
SELECT *: devolve colunas que a tela talvez não deveria ver.

O que é

Context engineering é decidir o que o modelo vê a cada passo. Na aula 1.4 você viu que o modelo só sabe o que está na janela de contexto daquela chamada. Em agentes de código, essa janela é montada a partir de várias fontes:

instruções fixas da própria ferramenta;
arquivos de instrução do projeto, como CLAUDE.md (Claude Code), AGENTS.md (padrão aberto usado por Codex, Cursor e outros), regras do Cursor e steering do Kiro;
os arquivos que o agente decide ler;
a saída de comandos e testes;
resultados de ferramentas e de servidores MCP;
skills: pacotes de instruções e scripts que só entram no contexto quando a tarefa pede;
o histórico da conversa, que vai sendo resumido quando a janela enche.

A qualidade do resultado depende mais desse conjunto do que do modelo escolhido. É a mesma ideia de prompt engineering, aplicada a um sistema que lê e age por conta própria.

Um bom arquivo de instruções

Curto, específico, mantido como código. Exemplo de um projeto fictício de API de agendamentos:

# Agenda+
API de agendamento de consultas. Visão geral: README.md.

## Estrutura
- api/: FastAPI (Python 3.12, uv). Rotas em api/rotas/, regras em api/servicos.py
- web/: Vue 3 + Vite

## Regras do projeto
- Toda rota nova exige permissão explícita (ver api/permissoes.py).
- Nunca registre CPF, telefone ou e-mail em log.
- Mudou tabela? Gere a migração (uv run alembic revision --autogenerate) e revise.
- Datas sempre em UTC no banco; converta só na tela.

## Comandos
- Testes da API: cd api && uv run pytest -q
- Testes do front: cd web && npm test


Repare no que ele não faz: não explica Python, Vue ou boas práticas genéricas. Só diz o que é específico deste projeto e que o agente erraria sem saber.

O que não colocar
documentação inteira (aponte o caminho do arquivo);
regras genéricas que o modelo já segue ("escreva código limpo");
segredos;
instruções contraditórias ou desatualizadas, que são piores que nenhuma.

Um bom teste: para cada linha, pergunte "o agente erraria sem isso?". Se não erraria, a linha só ocupa espaço.

Os recursos do Claude que entram no contexto

O Claude Code reúne, num só lugar, quase todas as peças acima. Para um agente de código, vale conhecer o papel de cada uma:

RECURSO	PARA QUE SERVE	QUANDO USAR
CLAUDE.md (e AGENTS.md)	Instruções fixas do projeto, lidas em toda tarefa	O que o agente erraria sem saber: comandos, regras, armadilhas
Skills	Pacotes de instruções e scripts que só entram no contexto quando a tarefa pede	Procedimentos longos e raros, como gerar um relatório num formato específico
Subagentes	Agentes auxiliares com contexto próprio, que devolvem só o resultado	Pesquisar em muitos arquivos ou fazer uma subtarefa sem encher o contexto principal
MCP	Ferramentas e dados de outros sistemas, por um protocolo padrão (aula 2.2)	Consultar ou agir em sistemas além do código
Hooks	Ações automáticas em momentos definidos (antes de rodar um comando, depois de editar um arquivo)	Verificações que não podem depender de o agente lembrar, como rodar o lint
Modo de planejamento	O agente propõe um plano e espera a aprovação antes de mexer em arquivos	Tarefas maiores, em que é mais barato corrigir o plano do que o código
Permissões	Define o que o agente pode fazer sem perguntar	Sempre: comece restrito e libere aos poucos

Os nomes variam de ferramenta para ferramenta, mas a ideia se repete em todas: instruções fixas, conhecimento sob demanda, ferramentas, automações e limites.

Contexto além do arquivo
Aponte exemplos: "siga o padrão de api/rotas/pacientes.py" vale mais que um parágrafo de explicação.
Divida tarefas grandes: cada subtarefa com contexto limpo. Subagentes fazem isso, trabalhando com o próprio contexto e devolvendo só o resultado.
Recomece a conversa quando ela ficar longa e confusa; um resumo do que importa num começo limpo rende mais.
Ligue só os MCPs necessários: cada ferramenta conectada ocupa contexto com a sua descrição.
Skills para o que é raro: instruções longas de uma tarefa específica (gerar um relatório no formato da empresa, por exemplo) ficam numa skill e só entram quando são usadas.
Harness: o arquivo é só uma parte

Tudo isso, em conjunto, é o harness de um agente de código: instruções, ferramentas, permissões, verificações, memória e o ciclo de execução. O arquivo de instruções é a parte mais visível, mas um agente confiável depende também das outras (aula 2.1).

Trechos úteis: por que contexto importa mais que o prompt solto (0:00 a 3:25); como se chegou aos agentes, dos assistentes sem ferramentas de 2022 ao MCP em 2024 (3:25 a 5:17); um agente é um modelo mais o harness, e o produto não é o modelo (7:10 a 11:00); definir um agente especializado em arquivo Markdown (11:05 a 12:00); skills como passo a passo reutilizável para o que precisa de previsibilidade (12:04 a 16:50); skill, agente solto e arquitetura híbrida (16:50 a 17:46); subagentes para não poluir a janela de contexto (17:47 a 21:20); quando usar cada um, inclusive quando nem é preciso um modelo (20:00 a 22:30).

3.3 Spec-driven development: especificar antes de gerar código
Concluída
Spec-Driven Development na prática: do zero ao código sem ferramentas prontas
balta · 40 min · conta para concluir a aula
00:56 · 87% assistido
O problema

Pedir "crie um sistema de agendamento de consultas" a um agente gera algum sistema. Mas não necessariamente o que você queria: quem pode marcar, com que antecedência, o que acontece quando o paciente cancela, como evitar dois agendamentos no mesmo horário? Cada lacuna, o agente preenche adivinhando, e as adivinhações só aparecem quando alguém usa.

A ideia

Em spec-driven development, a especificação vem antes e vira o contrato do trabalho:

Requisitos: o que o sistema deve fazer, escrito como histórias de usuário e critérios de aceite verificáveis.
Desenho técnico: como fazer, com tabelas, rotas, componentes, decisões e alternativas descartadas.
Tarefas: lista de passos pequenos, cada um verificável e ligado a um requisito.
Implementação: o agente executa tarefa por tarefa; cada uma termina com seus testes passando.

Pessoas revisam cada etapa antes da seguinte. Corrigir um requisito custa uma frase; corrigir um módulo pronto custa dias.

Como escrever critérios de aceite

Um formato muito usado, inclusive pelo Kiro, é o EARS: QUANDO (situação), o sistema DEVE (comportamento). Exemplos:

QUANDO o paciente tentar marcar um horário já ocupado, o sistema DEVE recusar e sugerir os três horários livres mais próximos.
QUANDO faltar menos de 24 horas para a consulta, o sistema DEVE enviar um lembrete por mensagem.
QUANDO o paciente cancelar com menos de 24 horas de antecedência, o sistema DEVE cobrar a taxa de cancelamento.

Repare que cada critério vira um teste quase direto. É assim que a spec se liga ao sinal de verificação da aula anterior.

Um pedaço de spec
## Requisito 3: cancelamento pelo paciente
História: como paciente, quero cancelar uma consulta pelo aplicativo
para não precisar ligar para a clínica.

Critérios de aceite
1. QUANDO o paciente cancelar com 24 horas ou mais de antecedência,
   o sistema DEVE liberar o horário sem cobrança.
2. QUANDO o paciente cancelar com menos de 24 horas,
   o sistema DEVE cobrar a taxa definida pela clínica e avisar antes de confirmar.
3. QUANDO a consulta já tiver acontecido, o sistema NÃO DEVE permitir o cancelamento.

Fora do escopo: remarcação (requisito 4).


A linha "fora do escopo" é tão útil quanto os critérios: impede o agente de "aproveitar e implementar" o que ninguém pediu.

Ferramentas
Kiro (AWS): gera e mantém requirements.md, design.md e tasks.md dentro do projeto e executa as tarefas.
GitHub Spec Kit: o mesmo fluxo como comandos para vários agentes.
Qualquer agente: dá para fazer à mão. Peça "antes de escrever código, escreva a spec e espere minha aprovação", ou use o modo de planejamento que várias ferramentas oferecem.
Quando vale a pena
VALE	EXAGERO
Funcionalidade nova com regras de negócio	Corrigir um texto ou um bug pequeno
Mais de um dia de trabalho	Protótipo descartável
Várias pessoas ou agentes no mesmo tema	Mudança que cabe numa frase
Para o Analista de IA, vale também para prompts

A mesma disciplina se aplica a um assistente ou agente: antes de escrever o prompt, escreva o que ele deve fazer, o que não deve, e os casos que definem "funcionou". Esses casos viram o conjunto de evals (aula 2.4).

Assista

O vídeo tem cerca de 41 minutos e faz o processo à mão, sem ferramenta pronta, com um encurtador de links. Trechos úteis: a estrutura de pastas e os quatro arquivos, constituição, especificação, plano e tarefas (1:34 a 5:19); a constituição, com a diferença entre regra e desejo ("código limpo" é desejo; "nenhum acesso a dados dentro do endpoint" é regra) e a cláusula de nenhuma dependência nova sem justificativa (5:19 a 9:37); a especificação, com problema, objetivo, histórias, requisitos com identificadores, casos de borda e o que está fora do escopo (9:37 a 18:26); a etapa de clarificação, em que o modelo age como analista cético e levanta de cinco a sete pontos ambíguos, cada um com opções e uma recomendação (18:26 a 23:44); o plano, com decisões numeradas e justificadas (23:50 a 28:35); tarefas pequenas, ordenáveis e verificáveis, cada uma com origem, dependência e "concluída quando" (28:35 a 31:24); a análise de consistência antes de implementar, que acha requisito sem tarefa, tarefa sem origem e plano que contradiz a constituição (31:24 a 34:26).

Relacione com esta aula: os requisitos com identificador e os critérios verificáveis são o mesmo princípio dos critérios QUANDO/DEVE. O vídeo também reforça duas dicas práticas: usar uma conversa nova a cada fase, para não carregar contexto à toa (24:15), e dar à tarefa um critério de aceite, senão "é só um sonho" (29:55).

Ressalvas.

A implementação é só de uma tarefa (a geração do código aleatório, 34:26 a 37:04), sem build nem execução (35:58): o vídeo não prova que o sistema todo funciona.
"Nunca edite a pasta do código; se o código está errado, o pedido está errado" (3:42) é uma regra do método do autor, não uma lei. Revisar e ajustar o resultado continua sendo parte do trabalho.
Números de tokens (24:28) e nomes de modelos (20:27, 36:45) mudam; o exemplo usa .NET, mas o método não depende da tecnologia.
Há divulgação de um workshop e de um desafio no começo (0:40 a 1:34), no meio (13:43 e 23:50) e no fim (a partir de 37:04); pode pular.
Para praticar

Escreva os requisitos de uma funcionalidade pequena, como "o cliente pode pedir a segunda via de um boleto pelo chat". Inclua uma história de usuário, pelo menos quatro critérios no formato QUANDO/DEVE (inclua um caso de erro) e uma linha "fora do escopo".

Quando vale a pena

Vale para funcionalidade nova com regras de negócio, trabalho de mais de um dia e várias pessoas ou agentes no mesmo tema. É exagero para corrigir um texto, um protótipo descartável ou uma mudança que cabe numa frase.

Para o Analista de IA, a mesma disciplina vale para prompts: escreva o que o assistente deve e não deve fazer e os casos que definem funcionou. Esses casos viram os evals.

GUARDE
A linha de fora do escopo impede o agente de implementar o que ninguém pediu.
Em qualquer agente, dá para pedir: escreva a spec e espere minha aprovação.

GUARDE

CENA 3 DE 5
Critério de aceite

Um critério bom segue o formato QUANDO (situação), o sistema DEVE (comportamento), e vira teste quase direto.

Vago
Verificável
RESPOSTA
O cancelamento deve ser fácil e justo para o paciente.
Não dá para escrever um teste a partir disso.
GUARDE
QUANDO a situação acontecer, o sistema DEVE fazer algo verificável.
Inclua casos de erro e uma linha de fora do escopo.

Aprender com exemplos

Em machine learning, o modelo ajusta milhões (ou bilhões) de números internos, os parâmetros, até que suas previsões batam com os exemplos. Treinar é isso: mostrar um exemplo, comparar a previsão com a resposta certa, corrigir um pouco os parâmetros e repetir milhões de vezes.

Os tipos mais comuns:

Supervisionado: exemplos com a resposta certa. "Este chamado é de faturamento", "este é de acesso". O modelo aprende a classificar os próximos.
Não supervisionado: sem resposta certa; o modelo encontra grupos e padrões sozinho, como segmentar clientes por comportamento.
Por reforço: o modelo tenta, recebe uma recompensa ou punição e melhora. É usado para ajustar LLMs a preferências humanas e, mais recentemente, para ensinar modelos a raciocinar em problemas com resposta verificável.
Como nasce um LLM
Pré-treino: o modelo lê uma quantidade enorme de texto e aprende a prever o próximo token. Ninguém precisa rotular, porque o texto seguinte é a resposta certa. É aqui que ele aprende gramática, fatos, código e padrões de raciocínio. Custa muito caro e leva meses de computação.
Ajuste para instruções: com exemplos de pedidos e boas respostas, o modelo aprende a seguir instruções em vez de só continuar o texto.
Ajuste por preferência e por reforço: pessoas (ou outros modelos) comparam respostas, e o modelo é ajustado para preferir as úteis, honestas e seguras.

O resultado é um foundation model: um modelo geral que serve de base para muitas tarefas.

Por que isso importa para o analista

Entender o treino explica comportamentos que você vai ver todo dia:

Data de corte. O modelo só sabe o que estava nos dados até certa data. Preços, leis, produtos e procedimentos novos não estão lá. Se a resposta depende de informação atual, ela tem que entrar pelo contexto.
Nada da sua empresa. Manuais internos, contratos e dados de clientes não estavam no treino (e não deveriam estar). Também precisam vir pelo contexto.
Plausível não é verdadeiro. O modelo foi treinado para produzir o texto mais provável, não para checar fatos. Daí a alucinação (aula 1.4).
Viés dos dados. Se os dados de treino tinham distorções, o modelo também tem. Isso importa em decisões sobre pessoas, como triagem de currículos ou crédito (aula 2.7).
Especializar sem treinar de novo

Quase nunca uma empresa treina um LLM do zero. Para especializar, há três caminhos, do mais simples ao mais caro:

CAMINHO	QUANDO USAR
Prompt	Mudar tom, formato e regras. Primeira tentativa, sempre.
RAG	Dar acesso a conhecimento que muda (manuais, artigos, políticas).
Fine-tuning	Mudar comportamento de forma consistente quando prompt e RAG não bastam: um formato muito específico, classificação em grande volume, ou um modelo menor e mais barato fazendo uma tarefa estreita.

Você já comparou RAG e fine-tuning em detalhe na aula 1.6.

Como escolher um modelo

Há dezenas de modelos, de vários fornecedores, abertos e fechados, grandes e pequenos. Escolher pelo ranking de um anúncio é o erro mais comum. Um caminho mais seguro:

CRITÉRIO	PERGUNTA
Qualidade na sua tarefa	Ele acerta os seus casos? (só medindo: aula 2.4)
Custo por tarefa resolvida	Não o preço por token, e sim quanto custa para resolver um pedido do início ao fim, contando tentativas e passos
Tempo de resposta	O usuário espera? Há etapas em que dá para usar um modelo menor?
Janela de contexto	Cabe o que você precisa entregar a cada chamada?
Privacidade e contrato	Onde os dados são processados? São usados para treino? Há opção corporativa?
Aberto ou fechado	Rodar um modelo aberto na sua infraestrutura dá controle, mas traz o trabalho de operá-lo
Disponibilidade	O que acontece se o fornecedor sair do ar ou descontinuar o modelo?

Três regras práticas:

Comece pelo modelo mais capaz que o orçamento permite, descubra se a tarefa é possível, e só depois tente modelos menores e mais baratos com os mesmos casos de teste.
Misture modelos: um modelo pequeno para classificar e rotear, um maior só para os casos difíceis.
Fixe a versão e troque de propósito, depois de rodar os evals.

Como nasce um LLM

Um foundation model passa por etapas. Avance e veja o que o modelo aprende em cada uma.

1
Pré-treino
Lê uma quantidade enorme de texto e aprende a prever o próximo token. Ninguém precisa rotular, e é a etapa mais cara.
2
Ajuste para instruções
3
Ajuste por preferência e reforço
GUARDE
Pré-treino ensina a prever o próximo token; os ajustes ensinam a ser útil.
O resultado é um modelo geral que serve de base para muitas tarefas.

CENA 1 DE 5
Como nasce um LLM

Um foundation model passa por etapas. Avance e veja o que o modelo aprende em cada uma.

1
Pré-treino
Lê uma quantidade enorme de texto e aprende a prever o próximo token. Ninguém precisa rotular, e é a etapa mais cara.
2
Ajuste para instruções
3
Ajuste por preferência e reforço
GUARDE
Pré-treino ensina a prever o próximo token; os ajustes ensinam a ser útil.
O resultado é um modelo geral que serve de base para muitas tarefas.

CENA 2 DE 5
Treino ou contexto?

O modelo tem data de corte e não conhece a sua empresa. Compare a pergunta sobre uma notícia recente sem e com o texto no contexto.

Só conhecimento do treino
Com a notícia no contexto
PERGUNTA
Por que as respostas mudam?
CONTEXTO ENTREGUE AO MODELO
Pergunta sem busca e sem texto.
RESPOSTA
Responde com segurança sobre a notícia da semana, mas inventa os detalhes.
A informação é posterior aos dados de treino, então o modelo completa com o que parece provável.
GUARDE
Informação atual ou interna precisa entrar pelo contexto.
Plausível não é verdadeiro: o modelo foi treinado para o texto mais provável.

CENA 3 DE 5
Especializar sem treinar

Quase nenhuma empresa treina um LLM do zero. Siga a ordem do mais simples ao mais caro.

1
Prompt
Muda tom, formato e regras. É a primeira tentativa, sempre.
2
RAG
3
Fine-tuning
GUARDE
Prompt primeiro, RAG para conhecimento que muda e fine-tuning por último.
